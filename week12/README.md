# 12주차 — OWASP 웹보안 개론

> ⚠️ **이 주차의 `template/`은 교육용 취약 버전(before)입니다.** 11주차까지 만든 쇼핑몰에 저장형 XSS와 시크릿 노출 취약점을 일부러 남겨뒀습니다. **절대 실제 서비스나 공개 URL(Vercel 등)로 배포하지 마세요.** 로컬 환경에서만 확인하고, 13~14주차에 직접 고쳐서 안전한 버전(after)을 만듭니다.

## 학습 목표

- OWASP Top 10이 무엇이고 왜 참고할 가치가 있는지 이해한다(암기가 아니라 "내 코드에도 있을 수 있다"는 감각).
- 저장형 XSS(Stored Cross-Site Scripting)가 실제로 어떻게 동작하는지 우리 코드에서 직접 확인한다.
- 시크릿(비밀 값) 노출이 하드코딩된 폴백 값과 잊혀진 디버그 엔드포인트, 두 가지 흔한 경로로 어떻게 생기는지 이해한다.
- `tsc`/`eslint` 같은 정적 분석 도구가 왜 이런 보안 취약점을 잡아내지 못하는지 이해하고, 코드 리뷰·보안 체크리스트·전용 스캐너(SAST)가 왜 별도로 필요한지 납득한다.

## template/ 폴더 안내 (11주차 대비 변경된 파일 — 전부 "취약하게 만든" 변경입니다)

- `app/notices/[id]/page.tsx` — 공지 내용을 `{notice.content}`(자동 이스케이프)가 아니라 `dangerouslySetInnerHTML`로 렌더링하도록 변경. 줄바꿈을 `<br>`로 보여주려는 의도였지만, 사용자 입력을 이스케이프 없이 그대로 HTML로 해석시킵니다.
- `auth.ts` — `secret: process.env.AUTH_SECRET || "dev-secret-please-change-me"`로 변경. 환경변수가 없을 때 쓸 하드코딩된 폴백 시크릿이 코드에 그대로 커밋되어 있습니다.
- `app/api/debug/env/route.ts` (신규) — 인증 없이 `MONGODB_URI`/`AUTH_SECRET`을 그대로 JSON으로 반환하는 디버그 엔드포인트. "배포 전에 환경변수 확인하려고 급하게 만들고 지우는 걸 잊은" 상황을 재현합니다.
- 그 외 파일은 11주차와 동일합니다(장바구니, 주문, 인증/RBAC 로직 등은 변경 없음).

### 확인해보기

```bash
cd template
cp .env.local.example .env.local
# MONGODB_URI, AUTH_SECRET 채우기 (7주차 참고)
npm install
npm run dev
```

**XSS 재현**: 로그인 후 공지사항 글쓰기에서 내용에 `<script>alert(1)</script>`를 넣고 저장한 뒤, 그 글의 상세 페이지를 열어보세요. 경고창이 뜬다면 취약점이 재현된 것입니다.

**시크릿 노출 재현**: 로그인하지 않은 상태에서 브라우저로 `/api/debug/env`에 접속해보세요. `.env.local`에 적어둔 값이 그대로 응답에 보인다면 취약점이 재현된 것입니다.

> `npx tsc --noEmit`, `npx eslint .` 모두 (clean `.next` 상태에서) **경고 없이 통과**합니다 — 이것이 이번 주의 핵심 포인트입니다. 두 취약점 모두 문법적으로는 완전히 정상적인 코드라서 정적 분석으로는 걸러지지 않습니다. 추가로 `next dev`를 실제로 부팅해 두 취약점이 실제로 재현되는 것(위 두 단계)을 확인했고, 나머지 라우트(`/`, `/products`, `/cart`, `/login`)도 정상 응답(200)하는 것을 확인했습니다.

## 보안 메모

- **저장형 XSS가 "저장형"인 이유**: 공격 스크립트가 DB에 저장되기 때문에, 그 글을 여는 모든 사용자(관리자 포함)의 브라우저에서 반복적으로 실행됩니다. 링크 하나만 보내면 실행되는 반사형(Reflected) XSS보다 파급력이 큽니다. 실제로는 세션 쿠키 탈취, 페이지 변조, 관리자를 속여 원치 않는 요청을 대신 보내게 하는 것(CSRF와 결합)까지 가능합니다.
- **왜 자동 이스케이프를 끄면 안 되는가**: React/Next.js는 `{content}`처럼 중괄호로 값을 렌더링할 때 기본적으로 HTML 특수문자를 이스케이프합니다. `dangerouslySetInnerHTML`이라는 이름 자체가 "위험하다는 걸 알고 쓰라"는 경고입니다 — 정말 필요하다면 DOMPurify 같은 새니타이저를 반드시 함께 써야 합니다(13주차에 직접 적용합니다).
- **하드코딩된 폴백 시크릿이 위험한 이유**: `AUTH_SECRET`은 로그인 세션(JWT)에 서명하는 키입니다. 이 값이 GitHub 등에 공개되면, 그 값으로 서명된 "나는 admin입니다"라는 세션 토큰을 공격자가 직접 만들어낼 수 있습니다 — 비밀번호를 몰라도 로그인 자체를 우회하는 셈입니다.
- **잊혀진 디버그/헬스체크 엔드포인트**는 실제 침해 사고에서 반복적으로 등장하는 원인입니다. "임시로만 켜뒀다가 지우는 걸 잊는" 실수는 개인 프로젝트든 실무든 똑같이 발생합니다.
- **정적 분석의 한계**: `tsc`는 타입이 맞는지, `eslint`는 코드 스타일/흔한 실수 패턴을 봅니다. 둘 다 "이 코드가 보안적으로 안전한가"는 원래 목적이 아닙니다. 이것이 코드 리뷰, 보안 체크리스트, 전용 보안 스캐너(SAST, Static Application Security Testing)가 별도로 필요한 이유입니다.
