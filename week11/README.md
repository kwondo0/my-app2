# 11주차 — 고급 예제 I 완성: 주문

`template/`은 10주차의 상품 카탈로그 + 장바구니에, 실제 결제(주문 생성)와 주문 내역 조회를 더한 것입니다. 이 주로 쇼핑몰 레퍼런스 프로젝트가 완성됩니다 — 12~14주차 OWASP 실습은 이 코드를 베이스로 진행합니다.

## 학습 목표

- 결제 대행사 연동 없이, "결제하기"를 실제 주문(Order) 생성으로 단순화해 핵심(인증·검증·소유권)에 집중한다.
- 상품 정보를 참조(ref)만 하지 않고 주문 시점의 이름/가격을 복사해서 저장하는 이유(가격 변동/상품 삭제와 무관하게 과거 주문 내역이 보존되어야 함)를 이해한다.
- 여러 사용자가 동시에 같은 상품을 주문해도 재고가 꼬이지 않도록, DB의 원자적 연산(`$inc`)으로 재고를 감소시킨다.
- 9주차의 소유권 검사(본인 글만 삭제 가능)를 새로운 도메인(주문)에 다시 적용해본다 — 이번엔 "본인 주문만 조회 가능".
- 이 소유권 검사가 빠지면 어떤 사고(IDOR)로 이어지는지 이해하고, 12~14주차 실습을 예고로 접한다.

## template/ 폴더 안내 (10주차 대비 추가/변경된 파일)

- `models/Order.ts` (신규) — 주문 스키마. `items`에 `productId`(참조)뿐 아니라 `name`/`price`를 그대로 복사해서 저장합니다 — 나중에 상품 가격이 바뀌거나 상품이 삭제돼도 "그때 얼마에 샀는지"가 보존되어야 하기 때문입니다.
- `lib/orders.ts` (신규) — `createOrder(userId, items)`, `getOrdersByUser(userId)`(항상 userId 조건으로 필터링), `getOrder(id)`.
- `lib/products.ts` — `decrementStock(productId, qty)` 추가. `$inc`(원자적 증감)를 사용해, "읽고 계산해서 다시 쓰는" 방식에서 생길 수 있는 경쟁 상태(race condition)를 피합니다.
- `lib/cart.ts` — `clearCart()` 추가(결제 완료 후 장바구니 비우기).
- `lib/actions.ts` — `checkoutAction` 추가. 로그인 확인 → 장바구니 쿠키를 DB 상품 정보로 다시 채움(가격/재고 재검증) → `Order` 생성 → 재고 감소 → 장바구니 비움 → 주문 상세로 이동.
- `app/cart/page.tsx` — "결제하기" 버튼이 이제 실제로 동작합니다(로그인 필요, 비로그인 시 로그인 유도).
- `app/orders/page.tsx` (신규) — 로그인한 사용자 본인의 주문 목록만 표시.
- `app/orders/[id]/page.tsx` (신규) — 주문 상세. 본인 주문이 아니면(admin 제외) 존재 여부까지 숨기고 404로 응답 — IDOR 예고편입니다.
- `components/SiteHeader.tsx` — 로그인 시 "주문내역" 링크 추가.

### 실행해보기

```bash
cd template
cp .env.local.example .env.local
# MONGODB_URI, AUTH_SECRET 채우기 (7주차 참고)
npm install
npm run dev
# 로그인 후 /products에서 상품을 담고 /cart에서 결제하기 → 주문 상세로 이동하는지 확인
# /orders에서 방금 만든 주문이 보이는지, 다른 계정으로 로그인해 그 주문 id로
# 직접 접근하면 404가 뜨는지 확인
```

> `npx tsc --noEmit`, `npx eslint .` 모두 (clean `.next` 상태에서) 통과를 확인했습니다.
> 추가로 `next dev`를 실제로 부팅해 확인했습니다: 비로그인 상태로 `GET /orders`와
> `GET /orders/<임의의 id>` 모두 `307`로 `/login`으로 리다이렉트되고, `/`, `/products`,
> `/cart`, `/notices`, `/login`은 모두 정상 응답(200)했습니다. 이 샌드박스에는 실제 MongoDB
> 클러스터가 없어 결제 성공 이후의 흐름(주문 생성 → 재고 감소 → 주문 내역 조회)까지는 직접
> 확인하지 못했으며, 이 부분은 본인 클러스터 연결 후 체크리스트로 확인해야 합니다.

## 보안 메모

- **소유권 검사는 "그 데이터를 다루는 모든 곳"에 반복해서 적용해야 합니다.** 9주차에서는 공지사항 삭제에, 11주차에서는 주문 조회에 똑같은 패턴(`ownerId === session.user.id`)을 적용했습니다. 도메인이 바뀌어도 원칙은 그대로입니다.
- **"없다"와 "권한이 없다"를 구분해서 알려주지 않습니다.** 본인 것이 아닌 주문 id로 접근하면 403(권한 없음)이 아니라 404(존재하지 않음)로 응답합니다. 403으로 응답하면 "이 id의 주문이 존재하기는 한다"는 정보 자체가 공격자에게 새어나갑니다.
- **이것이 왜 중요한가 — IDOR(Insecure Direct Object Reference).** 만약 `/orders/[id]` 페이지가 로그인 여부만 확인하고 소유권을 확인하지 않았다면, 로그인한 누구든 URL의 id만 바꿔서 다른 사람의 구매 내역(무엇을 샀는지, 배송지 등 확장 시)을 볼 수 있었을 것입니다. 12~14주차에는 이 프로젝트의 before(취약한 버전)/after(수정된 버전) 브랜치로 이 취약점을 포함한 5종(XSS, NoSQL Injection, IDOR, 시크릿 관리, Rate Limiting/보안 헤더)을 직접 공격해보고 고치는 실습을 합니다.

## 과제: SNS 버전으로 응용해보기

지금까지 만든 쇼핑몰의 패턴은 이름만 바꾸면 다른 도메인에도 그대로 적용됩니다. 과제로 다음 매핑을 참고해 SNS류 예제를 자유롭게 확장해보세요(구현은 선택 과제이며, 설계 아이디어만 제출해도 됩니다).

- 상품 목록/상세 → 게시물(Post) 목록/상세
- 쿠키 기반 장바구니 → 로그인 없이 쓸 수 있는 임시 저장(초안)
- 주문 생성 + 소유권 기반 조회 → "내가 쓴 글" 목록(본인 글만 조회/수정 가능)
- admin 예외 접근 → 신고된 게시물 처리 권한
